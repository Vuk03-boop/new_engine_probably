## Observations

- Physical-device enumeration order changed between two runs (NVIDIA first, then Iris Xe first). Probes must select the GPU by properties/extensions, never by index.
- Keep build directories short: MSVC object/PDB paths over ~250 characters break CMake try-compile. The project path itself is short enough; a deep scratchpad is not.

Code and verified commands: [phase0-probes/README.md](../../phase0-probes/README.md). Scene: ground + two boxes, 26 triangles; primary ray, sun shadow ray, sky miss; 1280×720; Khronos validation on.

| Pixel comparison of all four combinations and across rounds | **bit-identical** (max abs diff 0 over 921,600 px) |
| Negative control `PROBE_FAULT_LEAK=1` (leak pipeline) | both languages report 1 validation error (leaked `VkPipeline`) and exit 3, so the validation counter can fail |
| README command sequence run verbatim in `cmd` | first attempt failed (`cpp\build.bat` left the caller in `cpp\`); fixed with `pushd/popd`; rerun exit 0 |

Device facts (RTX 3050 Laptop, driver Vulkan 1.4.351): maxRayRecursionDepth 31, shader group handle size 32 bytes; BLAS 3,712 bytes, TLAS 2,048 bytes for this scene.

Timings (validation on; raw lines in `phase0-probes/results/runs.jsonl`): GPU AS build 0.122–0.124 ms, GPU trace 0.589–0.592 ms for every combination. Host pipeline creation 15–19 ms warm. Instance+device creation about 300 ms warm, 1.8 s on the first run after a rebuild. In an earlier, un-interleaved pair of runs the first pipeline creation took 307 ms (GLSL) and the second 68 ms (Slang). That was the order of the runs (cold then warm), not the shader language. The NVIDIA driver's on-disk pipeline cache was not controlled or cleared, so **cold-compile cost is NOT MEASURED**.

Interpretation: at this scale the language and shader-compiler choices make no observable difference to the output or GPU time. That is expected, because the GPU does the same work either way. The probe proves that both stacks work end to end on this laptop. It does **not** discriminate between them on performance. The choice should rest on the next, more realistic probe (asset loading, large AS/texture memory, iteration speed) and on ergonomics. Observed so far: C++ needed no lifetime workarounds but has no safety net. Rust's ash pNext/borrowed build-info lifetimes cost one restructuring. Release binaries are 58 KB (C++) and 339 KB (Rust).

**NOT RUN:** window/swapchain, event-loop responsiveness during cold compile, profiler capture (RenderDoc and Nsight are not installed), controlled pipeline-cache cold start, memory-budget checks, Bistro rendering, any performance claim.

## Bistro probe (probe v2, C++ and Rust)

Authorization: "Green light go ahead" (Bistro probe with the ufbx dependency). Code and verified commands: [phase0-probes/README.md](../../phase0-probes/README.md). Raw logs: `phase0-probes/results/v2/` (`runs.jsonl` has 24 validated runs, `runs_novalidation.jsonl` has 12).

### Changes from the minimal probe

- **FBX loader:** ufbx v0.23.0 (MIT or public domain). The upstream `ufbx.c`/`ufbx.h` in `phase0-probes/third_party/ufbx/` are SHA-256-identical to the copy bundled in the Rust crate `ufbx = "=0.11.4"`, so both languages parse with the same C code, compiled by their own toolchains. Load options: right-handed Y-up, meters, `MODIFY_GEOMETRY`. Every mesh instance is flattened into one BLAS. Normals are per-triangle geometric normals, computed on the host in f32 in the same operation order in both languages.
- **Camera and sun as push constants:** the first FBX camera and the first FBX directional light. The small scene keeps its old camera and sun (0.5, 1, 0.3), which is now normalized on the host.
- **Shading:** the closest-hit shader shades the side the ray hit. Bistro has one-sided and back-facing geometry.
- **Memory and timing:**
  - Device-local uploads through staging buffers.
  - BLAS built with `ALLOW_COMPACTION`, and its compacted size queried (not compacted).
  - Scratch freed before measuring.
  - `VK_EXT_memory_budget` device-local heap usage read before and after setup.
  - 1 cold + 5 warm trace dispatches with timestamps.
- **Diagnostics:** `PROBE_PICK` (C++ only) does a CPU brute-force pick of chosen pixels. `dds_budget.py` estimates texture memory from DDS headers.

### Results

| Check | Result |
|---|---|
| Builds (C++ `/W4`, Rust release) | both clean. C++ needed one fix for string literals mangled while inserting the pick code. Rust with ufbx compiled on the first attempt |
| Small scene against the v1 baseline | 4 of 921,600 px differ (max 210), all on one box-top silhouette corner. | Bistro load | 2,832,120 triangles, **exactly** the README's "Exterior total". 2,077,661 vertices, 1,296 meshes, 1,300 nodes, 1 camera, 1 directional light, 405 textures. Both languages list identical texture paths (the C++ file uses CRLF, the Rust file LF) |
| 24 validated runs: 3 rounds × {small, Bistro} × {C++, Rust} × {GLSL, Slang}, plus 12 Bistro runs without validation | all exit 0, 0 validation errors, 0 warnings, empty stderr |
| Images | **Bit-identical** across language, shader compiler, round and validation on/off, for both scenes |

**First Bistro image: a diagnosed, not guessed, darkness.** With the hardcoded sun, 60% of the frame was flat ambient and no sky was visible. `PROBE_PICK` showed that those pixels hit real Bistro façades (`paris_building_04`, doors and concrete) 9–22 m away, facing away from the sun. The street at 14.7 m had an up normal but lay in a building's shadow. The camera looks along the street, slightly down (forward (-0.32, -0.07, 0.95)). The FBX's own directional light (direction to sun (0, 0.876, 0.482)) is used now. The image is still mostly ambient, because the camera-facing façades are backlit and the probe has no sky or indirect light. That is correct for this shading model, not an error.

### Interpretation

- Both stacks load and trace a real 2.8 M-triangle scene correctly and identically on this laptop. **The GPU side cannot tell the languages apart**, because the GPU work is identical.
- Host differences are small and not attributable to the language:
  - The ~5% faster Rust FBX parse runs the same C file compiled with different flags (`cc` crate versus CMake Release).
  - Pipeline creation differs by about 1 ms.
- The deciding factors are therefore ergonomics and ecosystem, not performance:
  - **C++:** the Bistro extension went smoothly apart from a self-inflicted string-escaping bug in the diagnostic.
  - **Rust:** the port compiled on the first try and needed no lifetime restructuring this time. `ash` builder lifetimes caught a real category of pNext-chain mistakes during v1.
  - **Vendor SDKs:** C++ keeps direct access to DLSS/RTXDI/NRC SDKs, which come last per the contract. Rust keeps safety for the identity/versioning/lifetime-heavy engine core.
- Unexplained observation: instance + device creation takes about 1.0 s after loading Bistro, versus about 0.29 s with the small scene, in both languages and with validation off. Not investigated; it matters for the startup budget only if it persists in the engine.

### Gate 1 — event loop stays responsive during a cold compile (`window_probe`)

Setup:
- 1280×720 window, FIFO swapchain, animated transfer clear each loop iteration. The display runs at ~144 Hz (median frame 6.9 ms).
- The RT pipeline (4 stages) is created after 1.5 s, either inline on the main thread or on a background thread.
- A new specialization-constant value on the raygen stage defeats the driver cache. It is verified: the same fixed seed compiled in 100.9 ms and then 14.9 ms when warm.

| Arm | Compile | Longest frame during compile |
|---|---|---|
| main thread, 3× unique seed (control) | 53–89 ms | **53–90 ms**: the stall equals the compile |
| background thread, 3× unique seed + 3 more in the README runs | 57–112 ms | **7.4–9.9 ms**: no stall |

- Validation: 0 errors and 0 warnings in all runs.
- Handles: shader-group handles were valid in all runs.
- **Pass:** a background compile keeps the loop responsive, and the control proves the metric catches a stall.
- **Limits:**
  - Only raygen carries the seed, so the other stages may be served from the cache and cold numbers are a lower bound.
  - The pipeline is tiny.
  - One run had a 132 ms baseline frame before any compile, attributed to window-startup noise and not investigated.

### Gate 2 — textures and alpha testing (`rt_probe --textures`, `shaders/probe_tex.slang`)

What the textured path does:
- All 405 FBX textures are uploaded as BC1/BC3/BC5 images with full mip chains. Base colour and emissive use sRGB views.
- Textures are sampled bindlessly (`runtimeDescriptorArray`, non-uniform indexing) at mip 0.
- Per-corner UVs have V flipped.
- Base-colour BC3 (DXT5) materials are treated as alpha-tested. This is a heuristic: leaves, masked glass, curtains and string lights.
- Alpha-tested triangles go in a second, non-opaque BLAS geometry, with any-hit alpha tests on primary and shadow rays (separate hit groups, because the payloads differ). Output is sRGB.

### Gate 3 — profiler/capture

- **Method:** the RenderDoc Vulkan layer is loaded per process (`VK_ADD_LAYER_PATH` + `VK_INSTANCE_LAYERS`). `PROBE_RENDERDOC_CAPTURE` brackets the trace submission with the in-app API (`StartFrameCapture`/`EndFrameCapture`, `RENDERDOC_API_1_6_0`).
- **Controls:**
  - Requesting a capture without the layer fails loudly, which is the negative control.
  - Images under RenderDoc are bit-identical to normal runs.
  - RenderDoc 1.46 did not hide the RT extensions.

| Capture | Size | Replay check (`qrenderdoc --python tools/rdc_replay_check.py`) |
|---|---|---|
| small scene | 43 KB | local replay supported; actions = 6× `vkCmdTraceRaysKHR` (DispatchRay) + copy; 2 AS, 1 RT pipeline recorded |
| Bistro textured | **1.03 GB** | same action list; 2,136 chunks |

The AS builds happen before the captured frame, so they show as initial state, not as actions.

Automation took four attempts:
1. The script got no arguments, because `qrenderdoc` does not forward them.
2. A script edit put a literal line break inside a string.
3. The unquoted script path was split at the space in the user's path.
4. The capture layer was inherited by `qrenderdoc`, which crashed replay with `IsCaptureMode(m_State)`.

After two failed tries, the fixes came from a start marker and RenderDoc's logs. That crash opened two "RenderDoc Bug Reporter" dialogs; they were closed **without sending**, and the crash dumps remain in `%TEMP%\RenderDoc\dumps`.

**Pass for capture and replay.** **NOT RUN:** hardware performance counters or GPU trace profiling. RenderDoc is a frame debugger; Nsight needs the login. GPU timing continues to come from the probes' own timestamp queries.
